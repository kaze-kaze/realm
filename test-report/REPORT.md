# realm 故障转移版本测试报告

- 测试时间：2026-11-19，本机 Docker 内完成，全程不接触任何真实线路或服务器
- 被测「已合并版」：`kaze-kaze/realm` master `2729766`（昨天合并的故障转移）
- 被测「修复版」：已合并版加上本次测试中做的修复。测试时在分支 `fix/failover-hardening` 的工作区里；之后已合并进 fork 的 master 并发布为 **v3.0.0**（见第六节）
- 对照「原版」：上游 v2.9.6（`7e9f44c`）
- **同日中午更新：** 按你的决定去掉了「连续 2 次成功清零」规则，并在去掉后的构建上把故障转移、负载均衡、极端场景、误判统计、抖动对照和长稳重新跑了一遍。下文「修复版」的数字除注明外都来自这次重跑。3.1 的两张吞吐主表和长稳的内存对照是去掉规则之前测的，3.1 末尾附了去掉之后的复核。

## 结论

1. **主备切换的主路径可靠。** 进程被杀、黑洞、应用假死、回切、三节点链、IPv6、主备全挂等 22 项故障转移场景，修复版 19 项通过，另外 3 项是对设计局限的如实记录，没有失败项。默认参数下主节点黑洞后约 10 秒完成切换，切换全程新建 TCP 连接 0 失败。
2. **吞吐和资源占用与原版没有可测差异。** 单连接 TCP 117.9 对 118.4 Gbit/s，UDP 小包 727 对 711 千包/秒，短连接 5.3 万对 5.5 万/秒，都在轮次间波动之内。开启故障转移后空闲内存多 256 kB。去掉清零规则后又复核了一遍，结论不变。
3. **测试共发现 8 个问题，全部已修复并回归通过。** 4 个出在昨天合并的故障转移代码里，4 个是上游原版就有的。最值得注意的三个：
   - 上游的 UDP 串包：并发 UDP 会话多时，不同客户端的上游端口会重叠，回包送错人。5000 个会话时原版只送达 92.7%，另有 7806 个包送给了别的客户端；修复后全部送达，串包 0。
   - 主节点静默失效后，主上有数据在途的 TCP 连接会卡约 15 分钟，客户端不会重连到备。修复后 60 秒释放。
   - TCP 探测在丢包链路上远比 UDP 容易误判（丢包 20% 时 50 次对 2 次）。修复后降到 0~1 次。
4. **误判：** 修复版在丢包 ≤10% 的链路上没有误判（2%、5%、10% 三档各 200 个端点跑 25 分钟，TCP、UDP 均 0 次）。丢包 20% 时 30 个端点 10 分钟里 TCP 误切 0 次、UDP 3 次，这种链路本身已经严重劣化。
5. **「连续 2 次成功就清零」这条规则已按你的决定去掉。** 线路断、通各约 1 秒地抖动时，切走的时间从 20 秒以上（4 组里有 2 组在 33 秒的测试窗口内始终没切）降到 1~12 秒，UDP 送达率从 55%~73% 升到 83%~97%。丢包 ≤10% 的链路上误判仍然是 0；高抖动延迟的链路上 TCP 误判有所增加。数据见第二节。

## 一、发现的问题与修复

| # | 问题 | 来源 | 怎么发现的 | 影响 | 修复 | 修复后 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | UDP 老会话在「所有节点都判 down」时被挪到同样 down 的活动节点 | 故障转移代码 | 场景 FO-18 | 无意义的换线；换线后原节点的回包还会被当成旧包丢掉 | 只在活动节点存活时才换线 | 会话路径由 A→B→A 变为 A→B；新增单元测试和集成测试，集成测试在旧代码上会失败 |
| 2 | 配了 `through = ip:port` 时，UDP 探测与业务会话抢同一个本地端口 | 故障转移代码 | 场景 FO-19 | 探测等待回显期间，业务回包被探测套接字收走。往返 40ms、探测间隔 0.5s 时丢 8.4% | 探测只用 `through` 的 IP，端口由系统分配 | 20000/20000 送达 |
| 3 | 中继本机到主节点的临时端口耗尽，被判成主节点故障 | 故障转移代码 | 场景 EX-05 | 主节点健康却被判下线并切换 | 本机端口类错误记为「未知」，不计入失败 | 0 事件；溢出的连接逐条改走备，0 失败 |
| 4 | TCP 探测每轮只有一次建连机会，丢一个 SYN 就算失败 | 故障转移代码 | 误判统计 | 丢包 20% 时 30 个端点 10 分钟误切 50 次（UDP 只有 2 次） | 无应答时每隔 1/3 超时补发一次建连，每轮最多 3 次；被拒绝或应答不符仍立即判失败 | 同条件下 0~1 次；丢包 ≤10% 为 0 |
| 5 | 主节点静默失效后，有数据在途的已有 TCP 连接一直卡着 | 上游行为，但它让故障转移对长连接失效 | 补充测量 | 内核默认约 15 分钟才放弃重传，期间客户端不会重连到备。keepalive 只管空闲连接 | failover 端点的上游连接设置 TCP_USER_TIMEOUT，取 keepalive 判死所需的时间（默认 15s × 4 = 60s） | 50 条卡死连接在 60~61 秒全部释放；之前一直卡到客户端自己超时 |
| 6 | 句柄耗尽后 TCP 监听永久停止 | 上游 | 场景 EX-06 | accept 报 EMFILE 就退出监听循环，进程还在但该端口再也不接新连接，直到重启。原版同样如此 | accept 出错后退避重试（10ms 起，翻倍到 1s）；顺手把「给单条连接设 keepalive 失败就退出监听」也改成只影响那条连接 | 压力过后 600/600 成功；原版 0/600 |
| 7 | 每个 UDP 会话固定预分配约 200 kB 缓冲 | 上游 | 场景 EX-03 | 5000 个 UDP 会话占 1076 MB | 缓冲从 8 个包位起步，收满才翻倍，上限仍是 128 | 同样 5000 个会话 123 MB，吞吐持平 |
| 8 | 不同 UDP 会话的上游端口会重叠，回包送错客户端 | 上游 | 长稳测试里客户端收到了不属于自己的包，追查得出 | 上游给每个会话的套接字都设了 SO_REUSEADDR，内核自动分配端口时会把已被占用的端口再发一次。5000 个会话（Linux 默认端口范围）时 763 个套接字共用端口 | 只在配置了固定出口端口时才设 SO_REUSEADDR | 共用端口 0 个，串包 0 个，送达 92.7% → 100% |

问题 5 的修复带来一个行为变化，需要你知道：failover 端点上，如果后端 60 秒不读数据而中继又有数据要发给它，这条连接也会被关闭。这正是「应用假死」时想要的效果，但如果你有后端会故意长时间不读，可以把 `tcp_keepalive` 设为 0 关掉（keepalive 也会一起关）。

## 二、「连续 2 次成功清零」已去掉

这条规则原来的做法是：连续 2 次探测成功，就把之前的失败记录清零。测试发现它在线路短促抖动时让切换慢很多，你看过数据后决定去掉。现在的判定只有一条：最近 `window` 轮探测里有 `fall` 轮失败就判下线，失败不需要连续。节点经 `rise` 判定恢复时，失败记录清空，从头计数。

下面是去掉前后两个构建的实测对照。探测间隔 0.5s，把时间乘 6 大致对应默认 3s 间隔。

**随机相位的抖动**（每种 4 组）：

| 抖动 | 版本 | UDP 多久切走 | 抖动期间 UDP 送达率 | 新建 TCP 连接 |
| --- | --- | --- | --- | --- |
| 断、通各约 1 秒 | 去掉前 | 20.3s、30.3s，另 2 组在 33 秒的测试窗口内没切 | 55%~73%，平均 61% | 0 失败 |
| 断、通各约 1 秒 | 去掉后 | 1.3s、2.8s、10.8s、12.3s | 83%~97%，平均 90% | 0 失败 |
| 断、通各约 2 秒 | 去掉前 | 1.3s~1.8s | 95%~97% | 0 失败 |
| 断、通各约 2 秒 | 去掉后 | 1.3s~4.8s | 92%~97% | 0 失败 |

换算到默认参数：线路以 6 秒左右的节奏断断续续时，去掉前要 2 分钟以上才切走，期间 UDP 丢三到四成；去掉后是 8 秒到 75 秒。新建 TCP 连接两边都不失败，靠的是单连接重试。

**固定相位的抖动**（场景 FO-05，明细见附录 A）：

| 抖动 | 去掉前 | 去掉后 |
| --- | --- | --- |
| 断 1 秒、通 3 秒 | 不切，UDP 送达 80% | 切走，94% |
| 断 1 秒、通 1 秒，`fall = 2` | 不切，63% | 切走，94% |
| 断 1 秒、通 1 秒，`fall = 3` | 不切，62% | 不切，63% |
| 断 2 秒、通 1 秒；断 3 秒、通 3 秒 | 切走，94% | 切走，94% |

第三行两边都不切：这组的相位恰好让探测每 4 轮只失败 1 轮，达不到 5 轮里 3 次。同样的抖动换成随机相位，去掉后 4 组都能切走（上表）。

**误判对照**。同一套劣化链路，主节点是健康的，每格是「TCP 误切 / UDP 误切」次数，30 个端点 × 10 分钟：

| 链路状况 | 已合并版 | 去掉前 | 去掉后 |
| --- | --- | --- | --- |
| 无损、丢包 1% / 2% / 5%、突发丢包、延迟 100±80ms | 0 / 0 | 0 / 0 | 0 / 0 |
| 随机丢包 10% | 1 / 0 | 0 / 1 | 0 / 0 |
| 随机丢包 20% | 50 / 2 | 1 / 2 | 0 / 3 |
| 随机丢包 30% | 158 / 36 | 21 / 43 | 14 / 56 |
| 延迟 300±200ms | 12 / 0 | 4 / 0 | 11 / 0 |
| 延迟 500±300ms + 丢包 2% | 30 / 0 | 30 / 1 | 30 / 1 |

- 丢包 ≤10%：去掉后仍然没有误判。2%、5%、10% 三档另外各用 200 个端点跑了 25 分钟，TCP、UDP 都是 0 次。
- 丢包 20%~30%：与去掉前同一量级，UDP 略多，TCP 略少。
- 延迟 300±200ms：TCP 误切从 4 次增加到 11 次。这一档往返时间在 200~1000ms 之间，带 `tcp_expect` 的探测要两个往返，常常超过 1.5s 的默认超时；以前靠清零规则压住了一部分。这种线路要把 `timeout` 调大（见第五节），不该靠清零规则兜着。

去掉规则之前我还用一个实验构建做过同样的对照（丢包 20% 是 1 / 6，丢包 30% 是 15 / 45，延迟 300±200ms 是 14 / 0），与这次的结果一致。

### 3.2 故障转移的时间线

默认参数（间隔 3s、超时 1.5s、5 轮里 3 次失败判下线、连续 5 次成功判恢复、hold 30s）下主节点黑洞的完整周期：

| 阶段 | 实测 |
| --- | --- |
| 黑洞 → 全局切换 | TCP 10.1s，UDP 10.1s |
| 切换前这 10 秒里的新 TCP 连接 | 0 失败。每条先等 `tcp_timeout` 的一半（2s）再重试备，最大耗时 2.0s |
| 切换前这 10 秒里的 UDP | 发往主的包全丢，中断 10.2s |
| 主恢复 → 判定恢复 | 12.6s（连续 5 次成功） |
| 回切 | 距上次切换 31.5s（满足 hold 30s 之后） |
| 整个周期 TCP | 0 失败 / 6811 |

其余场景用加速参数（间隔 0.5s、超时 0.3s）跑，切换耗时：

| 故障 | TCP | UDP |
| --- | --- | --- |
| 进程被杀（端口拒绝） | 1.0~1.5s（看故障落在探测周期的哪个位置），新连接 0 失败 | 1.3~1.8s |
| 黑洞 | 1.8s，新连接 0 失败 | 1.8s |
| 应用假死（能握手不回数据），探测配了 `tcp_send` / `tcp_expect` | 1.8s | 1.8s |
| 健康端口失效但数据端口正常 | 1.5s，0 失败，主上 100 条长连接不断 | 1.8s，0 丢包 |

已有会话的行为符合设计：TCP 连接从不迁移；回切时留在备上的 100 条长连接 0 断开；UDP 老会话留在备上，新会话回主；UDP 换线后旧节点迟到的 781 个回包全部被拦下，客户端看到的乱序旧回包为 0。

## 四、已知局限（设计如此，本次未改）

- **默认的握手探测看不出应用假死。** 后端能握手但不回数据时，不配 `tcp_send` / `tcp_expect` 就不会切换（实测假死期间 192/392 失败且无切换）。要覆盖这种故障，探测必须带请求和期望应答。
- **UDP 探测要求目标是回显服务。** 目标不回显时所有节点都会被判 down，UDP 照常转发但不会切换；TCP 不受影响。
- **用了独立健康端口时，数据端口单独坏掉不会触发全局切换。** TCP 被拒绝时靠单连接重试仍然成功，UDP 无法感知。
- **`balance` 没有健康检查**，与 `failover` 互斥。
- **高延迟线路要调大 `timeout`。** 带 `tcp_expect` 的探测至少需要两个往返。
- **比探测超时还短的反复中断，探测基本看不到。** 探测每轮在超时内最多试 3 次，中断比超时短时总有一次能通。实测断、通各 0.3 秒（加速参数的超时也是 0.3 秒）：探测 5~6 轮才失败 1 轮，不会切换，UDP 只送达 64%，新建 TCP 连接不失败。对应到默认参数，是每次中断不超过 1 秒左右的高频抖动。这是为了在丢包链路上少误判做的取舍，与清零规则无关。
- **每条被重试的连接会打一行 warn 日志。** 满速短连接（3 万连接/秒）下主节点被杀，切换前的 1.5 秒里打了 4.3 万行。
- **上游的监听队列长度固定为 1024。** 连接洪峰或 RST 洪峰下内核会丢 SYN，客户端要等 1 秒重传。新旧版相同。
- **Windows 上 UDP 会话套接字遇到 ICMP 不可达会报 WSAECONNRESET**，上游原有行为，未处理。

## 五、配置建议

```toml
[[endpoints]]
listen = "0.0.0.0:5000"
remote = "10.0.0.4:3000"
extra_remotes = ["10.0.0.5:3000"]
network = { use_udp = true, tcp_timeout = 4 }

[endpoints.failover]
probe = ["10.0.0.4:3001", "10.0.0.5:3001"]
tcp_send = "GET / HTTP/1.0\r\n\r\n"
tcp_expect = "HTTP/1.1 204"
```

- 探测目标尽量放在落地端，并且带 `tcp_send` / `tcp_expect`，这样链路中断和应用假死都能发现。UDP 需要落地端有一个回显端口。
- `tcp_timeout` 保持 3~5 秒。主节点黑洞时，切换前的新连接要等它的一半。
- 线路高峰期丢包在 10% 以内时用默认参数即可。丢包更高时把 `timeout` 调到 2.5~3，或者 `fall = 4`、`window = 6`。
- 线路容易反复抖动时把 `hold` 调大（比如 300），避免每分钟来回切一次。
